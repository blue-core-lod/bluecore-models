Today

One class, four jobs

Every write to Blue Core goes through it: the API routes, the loader, bulk update and FOLIO.

  1. Partition: split the payload into Hub, Work, Instance and Other Resource subgraphs; keep anonymous descriptions inline.
  2. Reconcile identity: reuse a Bluecore URI via bf:derivedFrom, or mint one.
  3. Write authority: per resource, upsert, create if absent, or leave alone.
  4. Link: instanceOf, expressionOf, and the Other Resource join table.
Size1,407 lines, 45 commits
Tests82 passing, 93% branch coverage
Speed~105 ms per LC record
The comments are full of real domain reasoning, and save() is solid operationally. The problem is that its central ideas only exist in docstrings, not in types.

What you can't easily do

  • Ask what will this save do? without writing to the database.
  • See why a resource was kept, overwritten or skipped, except by reading the logs and seven predicates.
  • Pass a graph in and get it back unchanged.
  • Test the write policy without a Postgres fixture.

How it would feel with a Plan

# copies the graph, normalises it, classifies
# every resource; no database yet
plan = SavePlan.from_graph(
    graph, namespace, mode=Write(Kind.WORK))

# identities and actions; reads, writes nothing
resolved = plan.resolve(session)
print(resolved.render())  # a dry run of the save

# resolves again, then persists + links, with retries
plan.apply(session_maker)

Where the state lives now

Seven predicates decide what happens to a resource. Each reads a different mix of mutable fields, and some read the stored row.

The fields are set at different times (constructor, save(), minting), and a subgraph cache keyed on a hand-bumped _revision has to stay in step with all of them.
Subgraphs are bare Graphs, so _subject re-guesses which node each one is about, many times per save.

Disentangled: four layers, each with one job

Input

once, in from_graph
  • copy of the caller's graph
  • normalised (empty @id, inference, stripping)
  • then frozen

Policy

pure, no database
  • Mode: Ingest / Write(kind)
  • Kind and Role per resource
  • one "what is this cited URI?" rule

Database

resolve() reads; apply() writes
  • identity: derivedFrom lookup, minting
  • Action from role + stored row
  • persist and link, in the retry loop

Outcome

after resolve or apply
  • created_uri
  • render(): dry run, or logs
  • entries with their actions

A legible policy: one rule, in one place

"What happens to this resource?" is answered today by a flag, three predicates and the stored row's JSON. Afterwards it's a small pure function and a list of cases.

proposed  action(), illustrative

def action(entry, stored, mode) -> Action:
    if stored is None:
        return Action.INSERT
    match entry.role:
        case Role.REFERENCE | Role.STUB:
            return Action.KEEP
        case Role.PRIMARY if (mode.ingest
                and entry.original
                and not stored.is_stub):
            return Action.KEEP  # LC overlay: inherited
    return Action.UPDATE
Case("An Instance save names its Work",
     mode=Write(Kind.INSTANCE), kind=Kind.WORK, stored="full",
     expect=(Role.REFERENCE, Action.KEEP),
     says="Saving an Instance never overwrites its Work.")
One list of cases feeds pytest (no Postgres needed for role and action), the developer table and the cataloger page. Changing the policy means changing a row, and the diff shows it.

The main outcome

Today's behaviour, stated as a policy

Phase 0 writes each row as a test against today's code, and no phase changes one. Each row is a test case and a sentence, rendered as a developer table and a cataloger table.

SituationRole → ActionFor catalogers
API save of a new WorkPRIMARY → INSERTYour new Work gets a Blue Core URI.
An Instance save names its WorkREFERENCE → KEEPSaving an Instance never overwrites its Work.
LC record cites a resource it doesn't describeSTUB → INSERT or KEEPWe hold a placeholder, marked incomplete, until a real description arrives.
An LC record is loaded again after you edited itPRIMARY → KEEP inheritedYour edits are kept, but its links to subjects and agents are replaced with LC's.
Each row is marked chosen or inherited. Inherited rows are today's behaviour that nobody chose on purpose: the LC overlay rule, re-ingest links, Items, Hub labels. After the refactor, each decision is its own PR that changes one row.

How we get there

Five small PRs, behaviour preserved

Phase 0

Safety net

Policy statement as tests against today's code; diff harness over uploads/; coverage; benchmark.

Phase 1

Name the mode

Ingest / Write(kind) and Kind replace the flags.

Phase 2

Subject with subgraph

Entry; mint in one pass; drop _subject and the cache.

Phase 3

Classify once

Role, Action, one cited-URI rule; the same policy cases, without Postgres.

Phase 4

Plan / apply

SavePlan, read-only resolve(), render(), wrapper facade, input copied.

Each phase: no change in what's written (checked by the diff harness), no slower than ~105 ms per record, and the public API unchanged.
After: reload dev and stage from scratch, checking each record against render() and the policy tables, instead of repairing old data piece by piece.
